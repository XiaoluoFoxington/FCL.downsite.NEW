## 1. 项目目标与范围

新增一个轻量 Windows 系统托盘程序 `fdn-autosync-tray`，用于控制本地自动同步任务。

功能范围：

- 定时自动同步。
- 手动立即同步。
- 暂停和恢复自动同步。
- 锁定和解锁托盘菜单。
- 锁定时查看同步状态和详细状态。
- 浏览项目目录、数据目录、配置文件和日志。
- 修改同步、Git、WiFi、通知、外观等配置。
- 自定义托盘底图和状态角标。
- Windows 当前用户开机自启动。
- Windows Toast 同步结果通知。
- WiFi 连接、断开和可选忘记配置。
- 查看运行次数、上次同步结果和下次执行时间。

不负责重新设计项目的同步业务，不取代 GHA，也不要求 GHA 启动或依赖托盘程序。

## 2. 基本设计原则

1. **轻量优先：** 少依赖、少进程、少抽象。能用 Node.js 原生能力完成的，不引入框架。
2. **单一业务实例：** 同一时间最多有一个本地业务实例和一轮同步任务。
3. **同步逻辑复用：** 本地托盘和 GHA 调用同一套探测及同步业务代码。
4. **配置可迁移：** 程序目录可以整体复制到另一台机器；迁移后重新安装/修复自启动即可。
5. **失败可恢复：** Push 失败不回滚本地 Commit；下一轮能检测并继续推送。
6. **尊重用户工作区：** 不自动清理、重置或覆盖用户未提交的修改。
7. **界面与业务分离：** 托盘 UI 只发命令、展示状态，不直接执行 Git 或同步业务步骤。
8. **状态可信：** UI、通知和统计都读取结构化状态/结果，不解析日志文本推测状态。

## 3. 技术方案与进程模型

| 部分 | 选型 | 职责 |
|---|---|---|
| 同步业务 | Node.js 原生 ESM | 复用现有 `probe`、`sync` 业务逻辑 |
| 本地业务控制 | Node.js 原生 ESM | 调度、配置、状态、Git、WiFi、日志和通知编排 |
| Windows 托盘宿主 | Windows PowerShell | 创建托盘图标、菜单、处理 Windows UI 事件 |
| Git 操作 | Git CLI | Fetch、Pull、Commit、Push |
| 配置和状态 | JSON 文件 | 保存用户配置及少量运行状态 |
| 日志 | UTF-8 文本 | 记录阶段、错误和运行信息 |
| 通知 | Windows Toast | 显示同步结果 |
| 配置界面 | Windows 原生 WinForms | 提供设置窗口，不使用网页 UI |

Node.js 没有内置的 Windows 系统托盘 API，因此使用一个薄 PowerShell 托盘宿主和一个 Node.js 业务进程。这里所说的“单一业务实例”是指只有一个业务状态机和一个同步调度器，并不声称两个运行时处于同一个 OS 进程。

两者通过标准输入/输出的 JSON Lines 通信。不要建立复杂 IPC 框架，不需要独立 daemon、Named Pipe 服务、RPC 框架、Event Bus 或多层状态同步系统。

## 4. 建议目录结构

以下是目标结构示例。先检查仓库现状，尽量沿用合理的现有路径；若需要调整，应保持 GHA 入口兼容。

```text
scripts/
└── auto-sync/
    ├── probe.mjs                 # 现有探测入口，保持 GHA 可用
    ├── sync.mjs                  # 现有同步入口，保持 GHA 可用
    ├── ...                       # 现有同步业务模块
    └── local/                    # 本地托盘端
        ├── start.vbs             # 隐藏控制台启动入口
        ├── tray.ps1              # Windows 托盘宿主
        ├── main.mjs              # 本地业务入口
        ├── config.json           # 用户配置（本机数据，不提交）
        ├── state.json            # 运行状态（本机数据，不提交）
        ├── modules/
        │   ├── config.mjs        # 配置读取、校验、保存
        │   ├── scheduler.mjs     # 调度、暂停、恢复、互斥
        │   ├── sync-runner.mjs   # 六阶段同步流程编排
        │   ├── git.mjs           # Git 操作封装
        │   ├── wifi.mjs          # WiFi 操作
        │   ├── notification.mjs  # 通知和累积统计
        │   └── tray-icon.mjs     # 图标合成
        ├── assets/
        │   └── default.ico
        └── logs/
            └── YYYY/MM/DD/run.log
```

模块只按真实职责拆分，不要为了“架构完整”继续拆成大量很小的文件。缺乏独立复用价值的简单功能可以合并。

`config.json`、`state.json`、日志、用户图标等本机运行数据必须加入适当的 Git 忽略规则，不能意外提交到仓库。

## 5. 托盘菜单与锁定权限

### 5.1 普通状态菜单

菜单内容建议如下：

```text
fdn-autosync-tray
────────────────────────
自启动后已同步：12 次
上次同步：2026-11-26 12:30:00
上次结果：成功
下次同步：2026-11-26 12:40:00
────────────────────────
立即同步
暂停自动同步
锁定
────────────────────────
浏览 >
  项目目录
  下载数据目录
  自动同步目录
  最新日志
  日志文件夹
────────────────────────
配置文件
日志文件夹
配置
重启
退出
```

要求：

- 状态区域是只读信息，不可点击修改状态。
- 未执行过任何同步时，不显示虚构的上次同步时间或结果；可显示“尚未同步”。
- 暂停后将“暂停自动同步”改为“恢复自动同步”。
- 同步中将“立即同步”禁用或显示为不可重复触发。
- 下次同步时间来自调度器实际计划，不允许 UI 自行估算。
- 所有路径动态计算，不硬编码开发者机器上的绝对路径。

### 5.2 锁定状态菜单

**锁定时必须继续显示状态。** 锁定不是隐藏状态，也不是将托盘变成完全不可查看的状态。

锁定后菜单建议如下：

```text
fdn-autosync-tray（已锁定）
────────────────────────
自启动后已同步：12 次
当前状态：空闲 / 同步中 / 已暂停
上次同步：2026-11-26 12:30:00
上次结果：成功
下次同步：2026-11-26 12:40:00
────────────────────────
查看详细状态
────────────────────────
立即同步
解锁
浏览日志文件夹
```

锁定菜单权限：

- **允许查看：** 状态摘要、详细状态视图、日志文件夹。
- **允许操作：** 立即同步、解锁、浏览日志文件夹。
- **禁止操作：** 配置、打开/修改配置文件、暂停/恢复、重启、退出、切换图标、修改自启动等其他操作。

`查看详细状态` 必须是只读窗口，不提供修改配置、暂停、退出或其他控制按钮。至少展示：

- 当前运行状态：空闲、同步中、已暂停。
- 当前阶段（若正在同步）。
- 自启动后运行次数。
- 上次开始时间、结束时间、耗时。
- 上次结果和简短错误信息。
- 各结果累计次数。
- 下次同步时间；若暂停或正在同步且尚未安排下一轮，应如实显示“未安排”或“本轮结束后安排”。

锁定状态下右键菜单和详细状态窗口均不得泄露配置中的密码或 Token。

锁定后仍应允许托盘状态图标随同步状态变化。锁定不影响正在执行的同步，也不影响定时同步。

### 5.3 锁定密码

- 解锁需要输入密码。
- 密码错误时不解锁。
- 重启后仍保持锁定状态。
- 密码按用户的便携性要求存放在 `config.json` 中。
- 锁定只用于限制托盘 UI 操作，不是系统级安全边界，不能阻止用户直接访问文件或结束进程。

## 6. 托盘图标与状态角标

### 6.1 角标状态

| 状态 | 角标 |
|---|---|
| 同步中 | 白色向右三角形 |
| 暂停 | 白色 `||` |
| 上次成功 | 绿色勾 |
| 上次已是最新 | 绿色实心圆点 |
| 上次失败 | 红色叉 |
| 内部错误 | 红色叉 |

优先级：

1. 正在同步。
2. 已暂停。
3. 最近一次同步结果。
4. 初始默认状态。

因此，暂停时即使上次结果是成功，也优先显示暂停角标。锁定本身不覆盖同步状态角标；可通过菜单标题或锁定标记体现锁定状态。

### 6.2 合成规则

- 底图和角标分开处理。
- 角标在底图右下角，宽高约为底图的 50%。
- 透明挖空必须遵循角标实际形状轮廓，不可简单挖掉一个正方形。
- 边缘需要抗锯齿。
- 按 DPI 输出合适尺寸。
- 缓存键至少包含底图哈希、角标类型和输出尺寸。
- 状态变化时优先读取缓存，避免重复进行图片合成。

### 6.3 自定义图标

配置中提供“选择图片”和“重置默认图标”。支持常见 PNG、ICO、BMP 格式。

用户选择图片后，将图片复制到程序自己的 `assets/` 目录，不依赖原始图片路径。重置时恢复默认图标。图片损坏或无法解码时，提示用户并保留之前有效的图标。

### 7.2 明文凭据与迁移

按用户明确要求，以下内容直接保存在 `config.json` 中，允许明文：

- `H1111_SESSION`
- `GH_TOKEN`
- `PUSH_TOKEN`
- WiFi 密码

不使用 DPAPI，不绑定 Windows 用户账户，不因更换电脑而无法读取配置。

这是便携性与安全性的明确权衡：能够读取配置文件的人也可能读取其中的 Token 和密码。实现时必须：

- 不把 Token、Cookie、密码写入日志、异常消息或 Toast。

- 不把真实凭据放进测试样例、截图或提交记录。

### 7.3 配置管理

配置模块负责：

- 首次启动时生成默认配置。
- 读取和校验配置。
- 对旧版本配置做简单迁移。
- 保存配置。
- 恢复默认配置。

保存采用临时文件写入后替换原文件的方式。替换失败时保留原配置，并报告错误。

配置损坏时先备份损坏文件，再尝试恢复默认配置；不得静默清空用户设置。

### 7.4 配置页面

使用原生 WinForms 设置窗口，按以下分组组织：

**部署**

- Windows 当前用户开机自启动。
- 托盘外观。
- 选择图标、重置图标。
- 启动后同步一次。

**准备阶段**

- WiFi 管理总开关。
- SSID、密码。
- 优先使用 Windows 已保存密码。
- 不检查网络、总是尝试连接。
- 连接失败时跳过整次同步。

**Pull**

- 跳过 Pull 阶段。
- Pull 策略：rebase / ff-only。

**Sync**

- 跳过 Sync 阶段。
- `H1111_SESSION`。
- `GH_TOKEN`。

**Commit**

- 跳过 Commit 阶段。
- Git 身份：GHA / 默认 / 自定义。
- 自定义用户名和邮箱。

**Push**

- 跳过 Push 阶段。
- `PUSH_TOKEN`。

**结束阶段**

- 同步后断开指定 WiFi。
- 同步失败时是否也断开。
- 断开后是否忘记指定 WiFi 配置。

**通知**

- 标准模式 / 累积模式。
- 标准模式分别设置成功、已是最新、失败、内部错误是否通知。
- 累积模式设置累计次数。
- 内部错误始终弹出 / 不单独弹出。

**其他**

- 同步间隔。
- 日志保留天数。
- 锁定密码。

当前同步任务启动后应使用本轮配置快照。用户在任务执行中修改配置，只影响下一轮，不得中途改变正在运行的任务参数。

## 8. 同步流程

### 8.1 六个阶段

```text
Prepare
   |
   v
Pull
   |
   v
Sync
   |
   v
Commit
   |
   v
Push
   |
   v
Finish
```

| 阶段 | 职责 | 是否可跳过 |
|---|---|---|
| Prepare | 检查网络、按配置处理 WiFi | 按配置 |
| Pull | 获取远端更新并按策略整合 | 是 |
| Sync | 调用现有同步业务逻辑 | 可配置，默认开启 |
| Commit | 将生成的数据提交到本地 Git | 是 |
| Push | 将本地提交推送到远端 | 是 |
| Finish | 清理本轮资源、按规则处理 WiFi | 否 |

Sync 是项目自动同步的核心，必须复用当前已有业务实现。不得重新实现“获取资源、离线下载、获取直链、生成 JSON”等业务流程。

### 8.2 复用现有入口

优先保持仓库当前的 `probe`、`sync` 两个 GHA 入口。可根据真实代码将公共业务整理到共享模块中，例如：

```text
probe.mjs        # GHA / CLI 入口
sync.mjs         # GHA / CLI 入口
lib/             # 可复用的探测和同步业务
local/           # 本地托盘控制端
```

本地托盘和 GHA 调用同一份业务实现，只允许入口适配层处理环境变量来源、日志输出、Summary 和本地状态持久化等差异。

禁止复制一份 `sync-local.mjs` 并让它与 GHA 同步逻辑分别维护。

### 8.3 结构化结果

每轮同步必须返回结构化结果，不得通过解析日志文本决定状态。

状态只有四类：

- `success`：同步成功，有新内容或新版本。
- `up-to-date`：检查和同步成功，但没有需要更新的内容。
- `failure`：网络、远端服务、Git 等普通业务失败。
- `internal-error`：程序自身异常、配置/状态处理异常或关键运行时错误。

示例：

```js
{
  status: "success",
  startedAt: "2026-11-26T12:00:00.000Z",
  finishedAt: "2026-11-26T12:00:18.000Z",
  durationMs: 18000,
  message: "同步完成",
  stats: {
    resources: 2,
    versions: 3
  },
  error: null
}
```

失败示例：

```js
{
  status: "failure",
  startedAt: "2026-11-26T12:00:00.000Z",
  finishedAt: "2026-11-26T12:00:18.000Z",
  durationMs: 18000,
  message: "Push 阶段失败",
  stats: null,
  error: {
    stage: "push",
    code: "GIT_PUSH_FAILED",
    message: "远端拒绝了推送"
  }
}
```

错误消息不得包含 Token、Cookie、密码或敏感请求头。取消任务不能标为成功；若实现取消状态，应明确映射到用户可理解的失败/取消展示，且不要冒充上述四类中的成功结果。

### 8.4 Push 失败恢复

这是强制要求。

- Push 失败时不得回滚本地 Commit。
- Git 本地 Commit 本身就是待推送内容的持久化来源，无需额外 Pending Store。
- 下一轮检查本地分支相对远端跟踪分支是否存在 ahead commits。
- 有待推送提交时，按安全策略处理远端变化，然后再次尝试 Push。
- 如果远端有新提交，按配置策略 Pull；出现冲突时停止自动操作并记录冲突。
- 不得自动 `reset --hard`、`clean -fd` 或 `push --force`。

### 8.5 Git 工作区保护

每轮 Git 操作前检查：

- 当前目录确实是 Git 仓库。
- 当前分支、Remote、Upstream。
- 工作区和暂存区是否存在用户修改。
- 是否存在未完成的 Merge/Rebase/Cherry-pick。
- 本地与远端的 ahead/behind 情况。

规则：

- 不覆盖用户未提交修改。
- 不自动清理用户文件。
- 不自动重置分支。
- 不强制 Push。
- 不擅自修改 Remote URL。
- 不使用 `git config --global`。
- 自定义身份只作用于本仓库或本次 Commit。
- Pull 冲突时停止，不擅自选择 ours/theirs。

Git 命令使用 `spawn()` 参数数组并设置 `shell: false`，处理退出码、超时和 stdout/stderr。不得使用拼接命令字符串的方式执行 Git。

### 8.6 Git 身份

三种模式：

- `gha`：采用当前 GHA 脚本原有的身份设置。
- `default`：使用本机仓库当前 Git 配置。
- `custom`：使用配置文件中的用户名和邮箱。

本地托盘不得修改用户全局 Git 身份。

### 8.7 Token

按当前同步脚本的实际接口注入 `H1111_SESSION`、`GH_TOKEN`、`PUSH_TOKEN`。如果项目现有变量名或使用方式不同，以现有契约为准，不得擅自更改 GHA Secrets 名称。

- 不打印 Token。
- 不放入命令行参数。
- 不拼入 Git URL。
- 不写入异常信息、日志或通知。
- 不把 Token 复制到状态文件。

## 9. WiFi 管理

WiFi 管理是可选功能，默认关闭。

### 9.1 Prepare

启用后：

1. 记录开始时的网络和 WiFi 状态。
2. 检查默认路由、DNS 和 HTTPS 可达性，不只检查 WiFi 图标是否显示已连接。
3. 若网络正常且 `alwaysConnect` 为 false，可不切换网络。
4. 需要连接时，检查 Windows 是否已有目标 SSID 的保存配置。
5. 根据 `useSavedFirst` 决定是否优先使用已保存配置。
6. 必要时使用配置文件中的密码连接。
7. 检查连接结果。

### 9.2 连接失败

- `skipOnFailure = true`：跳过整轮同步，记为普通失败，并进入 Finish。
- `skipOnFailure = false`：继续尝试同步，让后续网络请求决定是否可用。

WiFi 连接失败不得导致程序崩溃。

### 9.3 Finish

支持：

- 同步结束后断开指定 WiFi。
- 同步失败时仍断开。
- 断开后忘记指定 WiFi 配置。

必须记录本程序是否实际建立了连接。**只有本程序为本轮同步新建立的目标连接，才允许由 Finish 断开。** 如果用户开始同步前就已连接目标 WiFi，程序不得擅自断开。

忘记配置必须精确限定目标 SSID，不能清理其他已保存的 WiFi。

## 10. 调度器

不要用永久 `setInterval()` 实现同步循环。每轮结束后根据完成时间安排下一轮。

### 10.1 调度规则

`intervalMinutes` 表示本轮结束后等待的分钟数。

例如：本轮 12:00 开始、12:01 结束、间隔 10 分钟，则下一轮为 12:11，而不是 12:10。

计算方式：

```text
nextRunAt = finishedAt + intervalMinutes
```

### 10.2 启动

- `runOnStart = true`：启动后立即执行一轮。
- `runOnStart = false`：直接安排下一轮。
- 如果已有实例运行，新实例退出，不创建第二个调度器。

### 10.3 暂停和恢复

暂停：

- 取消下一轮自动定时器。
- 不强制中止当前同步。
- 当前同步结束后不再安排自动任务。
- 手动立即同步仍可用。

恢复：

- 清除暂停状态。
- 从当前时间重新安排下一轮。

### 10.4 立即同步

- 不受暂停状态限制。
- 正在同步时拒绝重复启动，并向 UI 返回当前状态。
- 手动同步结束后重新计算下一轮计划时间。
- 不修改用户配置的同步间隔。

### 10.5 休眠与唤醒

电脑休眠可能使定时器延迟。唤醒后检查计划时间：

- 错过计划时最多补跑一轮。
- 不根据错过的时间连续补跑多轮。
- 本轮结束后恢复正常调度。

### 10.6 单实例与互斥

使用简单可靠的单实例锁，防止两个本地业务实例同时运行。同步任务本身还需互斥保护。不要构建通用锁服务。

## 11. 通知

### 11.1 标准模式

每轮结束后，根据结果类型和勾选项决定是否通知。

成功示例：

```text
自动同步成功
同步了 2 个资源，共 3 个版本。
```

已是最新示例：

```text
自动同步完成
当前已是最新，下次同步时间：11:45。
```

失败示例：

```text
自动同步失败
Push 阶段失败：远端拒绝了推送。
```

内部错误示例：

```text
自动同步内部错误
日志文件无法写入，请检查程序目录权限。
```

### 11.2 累积模式

从上次成功发送累积通知以后开始计数。达到 `everyRuns` 后发送汇总，例如：

```text
自动同步运行汇总
自上次通知后共运行 7 次：
成功：2 次
已是最新：4 次
失败：1 次
内部错误：0 次
```

配置内部错误是否始终单独通知。若通知发送失败，不能清空计数；只有发送成功才清零。

### 11.3 可靠性

通知失败不能改变同步结果，也不能让同步任务失败。Toast 不承诺 exactly-once，只做尽可能可靠的发送和去重。

## 12. 状态文件

`state.json` 只保存少量必要数据，不存储完整日志。

示例：

```json
{
  "version": 1,
  "locked": false,
  "paused": false,
  "totalRuns": 12,
  "lastRun": {
    "status": "success",
    "startedAt": "2026-11-26T12:00:00.000Z",
    "finishedAt": "2026-11-26T12:00:18.000Z",
    "durationMs": 18000,
    "message": "同步完成",
    "stats": {
      "resources": 2,
      "versions": 3
    }
  },
  "nextRunAt": "2026-11-26T12:10:18.000Z",
  "stats": {
    "success": 5,
    "up-to-date": 6,
    "failure": 1,
    "internal-error": 0
  },
  "notification": {
    "pendingRuns": 0,
    "success": 0,
    "up-to-date": 0,
    "failure": 0,
    "internal-error": 0
  }
}
```

要求：

- `totalRuns` 的计数时机必须统一，不能重复计数。
- 每轮结束时更新结果统计。
- 尚无 `lastRun` 时不显示虚假的上次同步记录。
- `nextRunAt` 表示调度器实际安排的时间；暂停时可为 `null`。
- 原子保存。
- 状态损坏时备份并恢复合理默认值，同时记录错误。
- 锁定状态必须持久化，重启后继续锁定。
- 详细状态窗口和锁定菜单只读取状态，不直接修改状态文件。

## 13. 日志

目录结构：

```text
local/logs/YYYY/MM/DD/run.log
```

日志等级：`DEBUG`、`INFO`、`WARN`、`ERROR`。

示例：

```text
[2026-11-26 12:00:00.123] [INFO] [Scheduler] 开始同步
[2026-11-26 12:00:00.456] [INFO] [Prepare] 网络检查通过
[2026-11-26 12:00:01.000] [INFO] [Pull] 开始 Pull
[2026-11-26 12:00:18.000] [INFO] [Push] Push 完成
[2026-11-26 12:00:18.100] [INFO] [Scheduler] 本轮同步结束：success
```

要求：

- UTF-8 编码。
- 按日期分目录。
- 支持日志保留天数。
- 保留天数为 0 表示永久保留。
- 只清理本程序自己的日志。
- 不记录 Cookie、Token、密码。
- 记录阶段开始/结束、耗时和结果。
- 日志写入失败不得直接导致同步业务崩溃；应尽可能通过 stderr/托盘提示错误。
- 锁定状态下允许浏览日志文件夹，但不开放其他配置或管理入口。

## 14. 启动、自启动、重启和退出

### 14.1 开机自启动

使用当前 Windows 用户 Startup 文件夹创建快捷方式，指向 `start.vbs`：

- 不要求管理员权限。
- 不写入系统级启动项。
- 禁用时删除本程序快捷方式。
- 程序移动后提供修复/重新生成快捷方式的能力。

### 14.2 启动流程

```text
start.vbs
   |
   v
tray.ps1
   |
   v
main.mjs
   |
   v
计算程序路径并加载配置
   |
   v
加载状态并检查单实例
   |
   v
创建托盘菜单
   |
   v
启动调度器
```

检查 Node.js 和 Git 是否可用；缺失时显示明确提示，不能静默退出。所有路径通过脚本自身位置解析，正确支持中文路径、空格和可移动目录。

### 14.3 重启

- 停止安排新任务。
- 当前同步未结束时，不得无提示强杀 Git/同步子进程。
- 可以等待当前任务安全结束，或让用户明确确认后安全取消。
- 保留配置、状态、日志和锁定状态。
- 重启不应意外重复执行启动同步；只有配置明确要求时才触发。

### 14.4 退出

- 取消未来的自动调度。
- 不再启动新任务。
- 正在同步时采用安全等待/明确确认取消策略。
- 保存最终状态并关闭托盘宿主。
- 锁定状态下“退出”不可见、不可操作。

## 15. PowerShell 与 Node.js 通信

PowerShell 负责：

- Windows NotifyIcon 和菜单。
- 菜单显示和刷新。
- 将菜单命令转发给 Node.js。
- 展示详细只读状态窗口。
- 打开 WinForms 配置窗口（仅未锁定时）。
- Windows 侧通知调用。

Node.js 负责：

- 同步业务和调度。
- 配置、状态读写。
- Git 操作。
- WiFi 管理。
- 日志和统计。
- 命令分发及权限校验。

通信采用标准输入输出 JSON Lines，每行一个 JSON 对象。

Node.js → PowerShell：

```json
{"type":"state","locked":false,"paused":false,"running":true,"stage":"sync"}
{"type":"result","status":"success","message":"同步完成"}
```

PowerShell → Node.js：

```json
{"type":"command","name":"sync-now"}
{"type":"command","name":"pause"}
{"type":"command","name":"unlock"}
{"type":"command","name":"get-status"}
```

要求：

- 每条消息独立解析。
- 非法 JSON 不得导致整个进程崩溃。
- stdout 只输出协议消息，诊断信息写 stderr 或日志。
- 不实现通用 RPC、Event Bus 或复杂消息队列。
- **Node.js 业务层必须再次校验锁定权限。** 不能只依赖 PowerShell 隐藏菜单项；即使收到不允许的命令，也必须拒绝。
- 锁定时仍允许 `get-status`、只读状态展示、`sync-now`、`unlock` 和打开日志文件夹相关命令。

## 16. 命令权限表

命令应集中由 `main.mjs` 分发。建议权限表如下：

| 命令 | 普通状态 | 锁定状态 |
|---|---:|---:|
| `get-status` / 查看状态 | 允许 | 允许 |
| 打开只读详细状态 | 允许 | 允许 |
| `sync-now` | 允许 | 允许 |
| `pause` / `resume` | 允许 | 禁止 |
| `lock` | 允许 | 不适用 |
| `unlock` | 不适用或允许 | 允许 |
| 打开日志文件夹 | 允许 | 允许 |
| 打开最新日志 | 允许 | 按 UI 设计；不得暴露凭据 |
| 打开项目/数据目录 | 允许 | 禁止 |
| 打开配置文件 | 允许 | 禁止 |
| 打开配置窗口 | 允许 | 禁止 |
| 修改图标/自启动/配置 | 允许 | 禁止 |
| 重启 | 允许 | 禁止 |
| 退出 | 允许 | 禁止 |

锁定时允许查看状态，不代表允许查看敏感配置。状态对象不得包含凭据、完整环境变量、Cookie 或其他秘密。

## 17. 模块职责

### `main.mjs`

本地业务入口，负责初始化、装配模块、命令分发、锁定权限校验、同步状态维护和进程退出。不承担具体 Git 命令实现或图标绘制。

### `config.mjs`

配置默认值、Schema/类型校验、版本迁移、读取、原子保存和恢复默认。

### `scheduler.mjs`

定时器、暂停/恢复、立即同步、互斥、下次执行时间及休眠唤醒补跑策略。

### `sync-runner.mjs`

组织六个阶段、处理跳过配置、调用共享同步业务、收集阶段结果、统一错误分类、确保 Finish 执行并返回结构化结果。

### `git.mjs`

封装 Git 命令、仓库检查、Pull、Commit、Push、ahead/behind 检查、冲突检测及身份设置。

### `wifi.mjs`

网络检查、SSID 检查、连接/断开、可选忘记配置，并记录本程序是否建立了连接。

### `notification.mjs`

标准/累积通知、结果统计、失败重试保留计数。

### `tray-icon.mjs`

底图、角标、Alpha Mask、DPI 和图标缓存。

### `tray.ps1`

Windows NotifyIcon、菜单、详细状态窗口、设置窗口入口和 JSON Lines 命令转发。PowerShell 端不直接执行同步或 Git 操作。

## 18. 异常处理

普通失败示例：

- 网络连接失败。
- WiFi 连接失败。
- 网盘 API 返回业务错误。
- GitHub API 请求失败。
- Git Pull 失败。
- Git Push 失败。
- 远端拒绝操作。

内部错误示例：

- 配置无法解析。
- 必要模块加载失败。
- 未处理程序异常。
- 关键状态无法保存。
- 关键运行时依赖不可用。
- 内部数据格式违反约定。

每个错误至少提供：

```js
{
  stage: "push",
  code: "GIT_PUSH_FAILED",
  message: "远端拒绝了推送"
}
```

特殊规则：

- 日志写入失败不得覆盖原始同步错误。
- 通知失败不得改变同步结果。
- WiFi 清理失败应作为清理警告记录；不能把已成功同步无条件改成普通同步失败。
- 用户主动取消不能标为成功。
- 锁定权限拒绝属于正常控制结果，不应伪装成内部错误。

## 19. 必须保持的 GHA 兼容性

**这是本次重构的最高优先级约束之一。**

先以仓库实际 `.github/workflows/` 工作流为准，确认现有自动同步是 probe + sync 双 Job 还是其他结构。若当前确为双 Job，则保持其核心行为和依赖关系。

不得破坏：

- 当前 `probe`、`sync` 入口路径和调用方式，除非有完全兼容的适配。
- Node.js 原生 ESM 运行方式。
- GHA 当前依赖安装假设（若当前无需 `npm install`，重构后也不能无故要求安装）。
- GHA Secrets 名称及其读取方式。
- 环境变量契约。
- Actions Summary、日志、注解和退出码语义。
- 工作流并发控制。
- Commit 行为和身份设置。
- JSON 数据格式及数据落盘目录。
- probe 无候选时跳过后续 sync 的原有行为（若当前工作流有此逻辑）。

托盘端不得：

- 强制 GHA 启动 PowerShell。
- 强制 GHA 安装 Windows 桌面依赖。
- 让 GHA 依赖本地 `config.json` 或 `state.json`。
- 将托盘运行状态提交到仓库。
- 让 GHA 只能通过托盘程序完成同步。

允许重构同步业务内部结构，但应保持现有 GHA CLI 入口兼容。差异应限制在入口适配层：GHA 负责 Actions 环境和输出，本地端负责本地配置、托盘状态和通知，共享同一同步核心。

## 20. 测试计划

### 20.1 配置测试

- 首次启动生成默认配置。
- 缺少字段时补齐默认值。
- 类型或枚举非法时给出可理解的错误。
- 损坏配置会备份，不会静默清空。
- 写入中断时原配置保留。
- 凭据不出现在日志。
- 移动程序目录后可读取配置。

### 20.2 调度测试

- 开机后立即同步。
- 开机后不立即同步。
- 同步间隔从本轮完成时间计算。
- 暂停后不再自动同步。
- 恢复后重新安排计划。
- 手动同步不受暂停限制。
- 同步中重复触发会被拒绝。
- 任务结束后重新安排下一轮。
- 休眠唤醒最多补跑一轮。

### 20.3 锁定测试

- 锁定后状态摘要仍显示。
- 锁定后仍能打开详细状态只读窗口。
- 详细状态窗口不会显示 Token、Cookie、密码。
- 锁定后仍能查看运行次数、上次结果、下次同步时间。
- 锁定后仍能立即同步。
- 锁定后仍能解锁。
- 锁定后仍能打开日志文件夹。
- 锁定后配置、暂停/恢复、重启、退出等命令被 UI 和 Node.js 双重拒绝。
- 重启后仍保持锁定。

### 20.4 Git 测试

使用本地 bare repository 模拟远端：

- 正常 Pull、Commit、Push。
- 无新内容返回 `up-to-date`。
- 本地 Commit 成功但 Push 失败。
- 下一轮能够重新 Push 成功。
- 远端有新提交。
- Pull 冲突。
- 用户存在未提交修改。
- 当前仓库没有 Upstream。
- 当前仓库处于 Rebase/Merge 未完成状态。
- 不会意外覆盖用户修改。
- 不会执行强制 Push、hard reset 或 clean。

“Push 失败后下一轮成功推送”必须是自动化回归测试。

### 20.5 同步与 GHA 测试

- 本地运行 probe。
- 本地运行 sync。
- GHA 原有方式运行 probe。
- GHA 原有方式运行 sync。
- 无候选时仍按原工作流逻辑跳过后续 Job（若原本如此）。
- 输出 JSON 格式不变。

## 22. 明确禁止的过度设计

| 不采用 | 原因 |
|---|---|
| Electron | 体积和运行成本过高 |
| SQLite | 少量配置和状态用 JSON 足够 |
| 独立 daemon | 没有必要 |
| Named Pipe RPC 框架 | 标准输入输出足够 |
| Event Bus | 当前业务状态简单，不需要 |
| 多层 Store | 增加状态同步成本 |
| Pending Store | Git Commit 本身就是待推送数据 |
| 插件化同步阶段 | 当前阶段固定，无需扩展框架 |
| 通用任务队列 | 同一时间只允许一轮同步 |
| 通用配置框架 | 普通 JSON 校验即可 |
| 复杂依赖注入容器 | 模块直接导入即可 |
| 过度抽象 Git 适配层 | 封装实际使用的 Git 命令即可 |
| 自行实现 Toast 系统 | 使用 Windows 原生通知能力 |

如果某个抽象不能明显降低当前代码复杂度、提高可靠性或避免重复实现，就不要增加它。

## 23. 推荐实施顺序

1. **仓库盘点：** 检查仓库指令、目录、同步入口和 GHA 工作流，输出当前行为清单。
2. **保护 GHA：** 为现有 `probe`、`sync` 和工作流建立基线测试或记录可验证的基线行为。
3. **配置与状态：** 实现 JSON 配置、校验、迁移、原子保存和状态文件。
4. **Git 模块：** 实现仓库检查、Pull、Commit、Push、冲突检测和 Push 失败恢复。
5. **同步编排器：** 实现六阶段编排，复用已有同步业务，返回结构化结果。
6. **调度器：** 实现单实例、同步互斥、自动调度、暂停、恢复和手动同步。
7. **日志与通知：** 实现脱敏日志、标准通知和累积通知。
8. **托盘宿主：** 实现菜单、状态刷新、锁定权限、只读详细状态视图和命令转发。
9. **配置窗口：** 实现所有配置页面。
10. **图标：** 实现底图、角标、Alpha Mask、DPI 和缓存。
11. **WiFi：** 最后接入，避免影响同步主链路。
12. **完整回归：** 验证 Windows 行为和 GHA 原有工作流。

每个阶段完成后先运行相关测试，不要等全部开发结束才开始验证。
